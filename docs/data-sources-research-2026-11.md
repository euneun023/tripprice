# 상품 데이터 공급처 조사 — 2026-11-03

목적: Tripprice가 상품 100개 수준에서 **수백~수천 개**로 확장하면서, 한국·일본
양쪽의 **실제 구매 가능한 가격**을 여러 판매처에서 지속 갱신할 수 있는 공급 구조를
확정한다. 기존 조사(`최종정리_서비스방향과_수익성-2.md`, `docs/phase1-design.md`)에서
이미 결론 난 항목은 재조사하지 않고, **미해결 조건**만 검증했다.

---

## 0. 이 조사의 신뢰 등급과 제약 (먼저 읽을 것)

이 세션은 클라우드 컨테이너의 네트워크 정책 때문에 **외부 사이트 직접 열람(fetch)이
차단**됐다. `webservice.rakuten.co.jp`, `developer.yahoo.co.jp`, `openapi.11st.co.kr`,
`www.linkprice.com` 모두 프록시에서 403/DNS 거부됐다. 따라서 **약관 원문 전체를 직접
읽은 항목은 없다.** 검색엔진이 공식 도메인 페이지에서 추출·인용한 발췌문에 의존했다.

등급 체계:

| 등급 | 의미 |
|---|---|
| **A** | 이 저장소의 코드/키로 실제 호출이 동작함이 확인된 것 |
| **B** | 공식 도메인 문서의 인용 발췌로 확인. 원문 전체·부칙 미열람 |
| **C** | 블로그/커뮤니티 등 2차 정보. 수치 충돌 있음 |
| **U** | UNKNOWN. 공개 자료로 확인 불가 → 문의 필요 |

**법적 권한(이용약관상 허용)과 기술적 접근성(호출 가능)은 분리해서 표기한다.**
기술 접근이 되더라도 권한이 U면 "실사용 가능 공급처"로 판정하지 않았다.

## 1. 결론 요약

1. **일본 쪽 대량 공급은 사실상 해결된다.** 라쿠텐 `商品価格ナビ製品検索API`가
   JAN·型番·최저가·판매상품수를 주고(쿼리당 최대 3,000건), 야후쇼핑 v3가 `jan_code`
   검색을 지원한다(분당 30회). 즉 **일본 내 다판매처 가격 집계는 JAN 기준으로 자동화
   가능**하다.
2. **한국 쪽이 병목이다.** 네이버 쇼핑 검색 API는 2026-07-31 종료(대체 없음),
   G마켓/옥션은 셀러 전용, 쿠팡 파트너스는 **키워드당 10건·발굴 불가**. 11번가 일반
   Open API(상품검색)가 유일한 현실적 2번째 한국 소스다.
3. **한일 동일상품 조인키는 JAN이 아니라 브랜드+型番(MPN)이다.** 쿠팡·11번가 API는
   GTIN을 주지 않고, GTIN은 거래품목 단위라 지역 구성품이 다르면 값이 달라진다.
   → **제품명에 모델번호가 노출되는 카테고리만 대량 자동화가 가능**하다. 이것이
   상품군 선정의 1순위 기준이며, 이 저장소의 429건 매칭 베이스라인이 이를 수치로
   뒷받침한다.
4. **일본 쪽 제휴 수익은 한국 거주자에게 사실상 막혀 있다.** 라쿠텐 어필리에이트는
   해외 계좌 송금 불가(국내 계좌만). 수익은 한국(쿠팡 파트너스 + AdSense)에서 나오고,
   일본 가격은 트래픽·신뢰 자산으로 취급해야 한다.
5. **판정: CONDITIONAL GO.** 수천 개 확장을 막는 것은 데이터 공급처가 아니라 (a) 쿠팡
   파트너스 실제 호출 한도, (b) 11번가 상업적 이용 권한, (c) 100% 사람 승인 구조다.
   세 개 모두 유료 결제 없이 검증 가능하다.

## 2. 공급처 검증 매트릭스

브리프의 10개 검증 항목 순서대로. `-` 는 해당 없음.

### 2.1 즉시 사용 가능 (A/B 등급, 권한 문제 없음)

#### (1) Rakuten Ichiba Item Search API — **운영 중 (A)**
- 검색·대량조회: 키워드/shopCode/genreId 검색. 이 저장소에서 가동 중.
- 가격·재고: 제공. `itemCode`가 식별자(기존 조사에서 확정).
- 식별자: JAN 없음(상품 단위). → 製品検索API와 조합해야 함.
- 상업적 가격비교: 수익 목적 이용 시 **楽天アフィリエイト 경유 링크 생성 + 제휴규약
  준수** 조건(이용약관 제3조, B). 가격비교 자체를 금지하는 문구는 확인되지 않음.
- 저장·재표시: 제6조에서 지적재산권은 라쿠텐에 귀속, 제3자 양도·서브라이선스 금지.
  제7조는 접근횟수·갱신빈도 등 **별도 제한을 부과할 수 있다**고만 명시. **제10조
  禁止事項 전문은 열람 못 함 → 저장/DB화 조항 유무 U.**
- 갱신·호출: 버스트 시 429 확인됨(PoC). 순차·저속 배치 전제.
- 한국 거주 개인: 가능(현재 가동 중).
- 비용: 무료.
- 상품군: 라쿠텐 이치바 전 품목.
- 제휴·정산: 보수는 **일본 국내 계좌만**, 해외 송금 불가(공식 FAQ 인용, B).
  → 현금화 사실상 불가. 단, 제휴링크 사용으로 **약관 준수는 가능**.

#### (2) Rakuten 商品価格ナビ製品検索API (楽天プロダクト製品検索, version 2025-08-01) — **미사용·즉시 투입 권장 (B)**
이번 조사의 **가장 가치 있는 발견**이다. 현재 저장소에 연결돼 있지 않다.
- 검색·대량조회: 키워드 / **genreId** / 製品ID / **製品コード(JAN)** 중 하나 필수
  (JAN은 다른 검색 파라미터와 병용 불가).
  `hits` 1~30(기본 30), `page` 1~100 → **검색키 1개당 최대 3,000건**, 장르 순회로 수만 건 발굴 가능.
- 엔드포인트(B, 2026-11-03 확인):
  `https://openapi.rakuten.co.jp/ichibaproduct/api/Product/Search/20250801`
  — Ichiba Item Search의 `ichibams` 경로와 **호스트 경로가 다르다**(`ichibaproduct`).
- 응답 필드명(B): `productNo`(**型番** = 제조사 모델번호), `makerName`(회사명),
  `productCode`(JAN), `salesMinPrice`·`salesMaxPrice`·`averagePrice`·`salesItemCount`,
  `itemCount`·`minPrice`·`maxPrice`. 값이 없으면 **null** 반환.
  `formatVersion=2`로 배열 평탄화, `elements`로 필드 선택 가능.
- 인증: 구버전과 달리 **accessKey 필수**(이미 `.env`에 보유 → 추가 가입 불필요 가능성 높음).
  2026-02 라쿠텐 API 전면 이관(`openapi.rakuten.co.jp` + accessKey 필수, 구키 비권장)의
  일부이고, 이 저장소는 Ichiba 쪽을 이미 이관 완료한 상태다.
- 권한/저장: Rakuten Web Service 공통 약관 적용 → (1)과 동일, 제10조 U.
- 비용: 무료.
- 용도 판정: **캐노니컬 카탈로그(브랜드+型番+JAN+대표 최저가) 생성기.** 지금 수동
  시드로 100개를 채우는 작업을 이 API가 대체한다.

> **정정 (2026-11-03, 같은 날 추가 조사)** — 이 문서 초판에서 "detail에 型番 포함",
> "`itemCount`/`salesItemCount`로 판매처 수 파악"이라고 쓴 부분을 아래로 교체한다.
>
> 型番은 `ProductDetails`(detail) 안이 아니라 **최상위 `productNo` 필드**로 반환된다
> (공식 문서 발췌, B). 그리고 **2026-03-25 라쿠텐 공지**로 이 API의 일부 응답값이
> **공백/null로 반환**되도록 바뀌었다는 정황이 있다 — 대상: `ProductDetails`,
> `rankTargetGenreId`, **`itemCount`**, `usedExcludeCount`, `usedExcludeSalesItemCount`,
> **`minPrice`**, `usedExcludeMinPrice`, `usedExcludeSalesMinPrice`. `sort`의
> `-releaseDate`·`-seller`도 비권장 처리.
> 단 이 공지는 **공식 블로그의 Tumblr 미러 1건에서만 확인**됐고 재검색으로 교차확인에
> 실패했으며(C등급), 공식 문서 페이지는 여전히 해당 필드들을 명시하고 있다. 즉 **충돌 상태**다.
>
> 실무상 결론: **`salesMinPrice`와 `salesItemCount`는 공백화 목록에 없으므로 살아남았을
> 가능성이 높지만, 확인되지 않았다.** 따라서
> - "구매가능 N건 중 최저가" 표기는 **`salesItemCount`가 실제로 값을 반환하는지 확인한 뒤에만** 쓴다.
> - `itemCount`·`minPrice`는 **처음부터 없는 것으로 간주**하고 설계한다.
> - 어댑터(`src/adapters/rakutenProduct.ts`)는 모든 수치 필드를 `number | null`로 받고,
>   `salesItemCount`가 null이면 판매처 수를 **0이나 1로 대체하지 않고 "unknown"으로** 유지한다.
> - 이 한 건은 `npm run verify:rakuten-product` **라이브 1회 호출로 확정된다**(아래 §8 #2).

#### (3) Coupang Partners Open API — **운영 중, 구조적 한계 확인 (A)**
- 검색: 키워드 검색만. **`limit` 최대 10** (`src/adapters/coupang.ts:111`,
  초과 시 rCode≠0 + 빈 결과). 카테고리 브라우징/대량 덤프 **없음**.
  → **한국 쪽 상품 "발굴"에는 쓸 수 없고, 이미 아는 상품을 "확인·가격취득"하는 데만 쓴다.**
- 가격·재고: 가격 제공. 재고는 명시 필드 없음(기존 조사). 배송비는 boolean만.
- 식별자: `productId`뿐. **JAN/EAN/MPN 없음.** productUrl은 식별 불가(기존 확정).
- 상업적 가격비교/저장: 공식 약관 문구 **확인 불가(U)**. 파트너스 문서가 로그인 뒤에
  있어 이 저장소도 공식 스펙 접근이 없다(어댑터 주석에 명시).
- 호출 제한: **C등급·충돌.** "시간당 10회"와 "분당 50회"가 동시에 유통됨. 403 3회 시
  계정 API 제한 보고도 있음. → **실측 필수.** 어댑터가 이미 rate-limit 헤더를 수집하고 있음.
- 한국 거주 개인: 가능(이미 승인·가동). 단 API 활성화에 **누적 판매액 15만원** 요건 보고(C).
- 제휴·정산: 원화 정산, 한국 계좌. 실효 수수료 1~3%(기존 조사).

#### (4) Yahoo! Shopping 商品検索(v3) — **기술적으로 최적, 권한·계정이 관문 (B)**
- 검색: 키워드 + **`jan_code`** + ジャンル/ブランド/ストアID. "일본 최대급 상품 DB".
  → JAN 하나로 **여러 스토어의 현재가가 한 번에** 나온다. JP 다판매처의 정답.
- 가격·재고: 제공. 2026-08 로하코 상품 편입 등 **현재도 활발히 유지보수 중**(changelog 2026).
- 호출 제한: **appid당 분당 30회**(2022 변경 공지, B) + 문서상 "1쿼리/초" 권장, 초과 시 429.
- 상업적 이용: **기본 방침이 "이용자 자신의 편의를 위한 비상용 목적"**이며, 법인이
  상업적으로 쓰려면 **각 API 문의창구에 상담**해야 한다(공식 헬프 인용, B).
  금지행위: 웹서비스 접근에 과금, 해당 앱 판매. 크레딧 표시 의무.
  → **가격비교 사이트 운영이 허용되는지는 명시 없음 = U. 문의로만 해결 가능.**
- 한국 거주 개인: **Yahoo! JAPAN ID 개설이 선행 관문.** 공식 헬프는 "해외 휴대폰
  번호로는 SMS 인증 이용 불가"라고 기재(B). 최근 커뮤니티엔 국가번호 선택이 된다는
  비공식 보고도 있음(C). → **계정 개설 가능성 자체를 먼저 확인해야 한다.**
- 제휴·정산: ValueCommerce 경유. 등록 시 일본 금융기관·지점 선택 구조 → 해외 거주자
  가능 여부 U, 사실상 어려움으로 추정.

#### (5) 11번가 일반 Open API — 상품검색 (B 기술 / U 권한) ★한국 2번째 소스 후보
- 검색: 서비스코드 `ProductSearch`, 키워드+페이지. **`pageSize` 기본 50, 최대 200.**
  → 쿠팡(10건)의 **20배** 효율. 한국 쪽 발굴·갱신 병목을 완화할 유일한 공개 수단.
- 응답: 상품코드·상품명·이미지·상세URL·**가격·판매자**·평점·할인가·배송·리뷰수·혜택.
  → 오픈마켓이라 **동일 상품에 복수 판매자**가 잡힌다(한국 내 다판매처 비교 가능).
- 식별자: GTIN 없음(상품코드만).
- 키 발급: **셀러 전환 불필요.** "서비스등록"에서 사용자정보 입력 후 OPEN API KEY 발급,
  호출 시 헤더 포함. 일반 Open API는 **상품·카테고리 조회만** 가능(B).
  → 쿠팡과 달리 **판매 실적 요건이 없다.**
- 상업적 가격비교/저장/호출제한: **전부 U.** 약관 페이지 본문 미확인.
- 비용: 공개 자료상 무료(U).
- 제휴·정산: 11번가 자체 어필리에이트는 확인 못 함. 애드픽 '쇼핑메이트'에 11번가가
  연동된 사례 있음(C) → 수익화 경로 후보.

#### (6) 환율 API — 운영 중 (A). 변경 없음.

### 2.2 조건 확인이 필요한 공급처 (U — 문의 전에는 채택 불가)

| 공급처 | 무엇을 주는가 | 왜 아직 U인가 |
|---|---|---|

## 3. 식별자 전략 — 이번 조사의 구조적 결론

```
일본 내부 비교        : JAN으로 해결된다 (자동화 가능, 비용 0)
  Rakuten 製品検索(製品コード=JAN) ─┐
  Yahoo 商品検索(jan_code)         ─┴→ 같은 JAN의 여러 스토어 가격

한국 ↔ 일본 비교      : JAN으로 해결되지 않는다
  쿠팡 API: productId만, GTIN 없음
  11번가 API: 상품코드만, GTIN 없음
  GTIN 원칙: 판매국과 무관하게 유효하나, 브랜드 소유자가 '거래품목' 단위로 부여
             → 지역 구성품/번들/보증이 다르면 다른 GTIN (GS1 매뉴얼 기준, 추정 포함)
  ⇒ 조인키 = 브랜드 + 型番(MPN) + (최초 1회 사람 승인)
```

**따라서 "한일 양국에서 실제 비교 가능한 상품 수"는 "확보 가능한 상품 수"보다 훨씬
작고, 그 비율을 결정하는 것은 카테고리다.** 모델번호가 상품명에 박히는 카테고리는
비율이 높고, 그렇지 않은 카테고리는 사람 검수 비용이 상품 수에 비례해 폭발한다.

## 7. 수천 개까지 확장하기 위한 조건 (정량)

1. **발굴 한도는 문제가 아니다.** 라쿠텐 製品検索 장르 순회로 수만 건 확보 가능.
2. **한국 쪽 호출 예산이 전부를 결정한다.**
   - 쿠팡: 1상품당 1콜(키워드당 10건). 분당 50회면 **일 72,000콜 → 수천 개 일일 갱신
     가능**. 시간당 10회면 **일 240콜 → 1,000개 카탈로그의 1회전에 4일 이상**.
     → 이 한 숫자가 서비스 상한선이다. **실측 전에는 상품 수 목표를 확정할 수 없다.**
   - 11번가: pageSize 200 → 같은 예산으로 20배 효율. 한국 쪽 호출제한 U.
3. **100% 사람 승인 구조는 수천 개와 양립하지 않는다.**
   현 설계는 "이름 기반 완전자동 매칭 미채택 + 최초 1회 사람 승인"이다(의도된 안전장치).
   수천 개로 가려면 **좁은 자동승인 레인**이 필요하다:
   브랜드 일치 + 型番 토큰 완전일치 + negativeFilter 통과 + 가격이 일본 환산가의
   합리적 밴드 내 → `confidence='estimated'`로 자동 생성하고 **공개 전 샘플 감사**.
   저장소에 이미 `identifierMatch.ts` / `modelTokenSuggestion.ts` / `negativeFilter.ts`
   와 429건 베이스라인이 있어 **임계치를 실측으로 정할 수 있다.**
4. **확장은 카테고리 단위로만 한다.** exact율 75% 미만 카테고리는 자동승인 레인을 열지 않는다.
5. 라쿠텐 제10조(저장/DB화) 확인이 끝나기 전에는 price_history 보존기간을 늘리지 않는다.

## 11. 최종 판정

### **CONDITIONAL GO**

**GO 근거**
- 일본 쪽은 JAN 기준 다판매처 집계가 **공식 API로 자동화 가능**하고, 발굴 상한이
  쿼리당 3,000건 수준이라 **수천 개 카탈로그 자체는 데이터 공급 문제가 아니다.**
- 한국 쪽도 쿠팡(가동 중) + 11번가(셀러 전환 불필요 self-service)로 **2개 소스**가
  현실적으로 확보 가능하다.
- 자체 429건 실측에서 상위 카테고리 매칭 정확도가 **75~92%**로 확인됐다 — 즉
  "비교 가능한 상품"을 만드는 엔진이 이미 작동한다.
- 수요도 추정이 아니라 **공식 통계**로 뒷받침된다(일본 직구 +33.8%, 타 국가는 감소).

**조건 (이게 안 풀리면 수백 개에서 멈춘다)**
1. **쿠팡 파트너스 실제 호출 한도** — 시간당 10회라면 한국 쪽 갱신이 수백 개에서
   막힌다. 11번가로 대체/보완이 필수가 된다.
2. **11번가 상업적 이용 권한(U)** — 거절되면 한국은 쿠팡 단독, 즉 "한국 내 복수
   판매처 비교"가 불가능해지고 서비스 가치가 절반으로 떨어진다.
3. **자동승인 레인** — 100% 사람 승인으로는 수천 개가 성립하지 않는다.
4. **라쿠텐 제10조 / 야후 상업이용** — 저장·재표시 권한의 마지막 공백.

**HOLD가 아닌 이유**: 네 조건 모두 **유료 결제나 계약 없이, 기존 자산으로 1~2주 안에
판정 가능**하다. 특히 1·3번은 외부 회신을 기다릴 필요조차 없다.

**GO가 아닌 이유**: 현재 UNKNOWN인 권리 항목(쿠팡 약관, 11번가 약관, 야후 상업이용,
라쿠텐 제10조)을 CONFIRMED로 바꾸지 않은 상태에서 상품 수를 수천 개로 늘리면,
사후에 전체 데이터를 걷어내야 하는 리스크를 안고 가는 셈이 된다.

## 부록 B: 이 세션에서 추가한 코드 (2026-11-03, 무인 실행분)

조사 결론을 실행 가능한 상태로 만들기 위해, 승인·외부 호출·결제가 필요 없는 범위에서
아래를 구현했다. **전부 읽기 전용이거나 dry-run 기본값이며, 라이브 호출은 명시적
플래그가 있어야만 일어난다.** 운영 DB·main·배포는 건드리지 않았다.

| 파일 | 역할 | 테스트 |
|---|---|---|
| `src/adapters/rakutenProduct.ts` | 商品価格ナビ製品検索API 어댑터. 검색키 1개 강제, hits/page 범위 로컬 검증, 모든 수치 필드 `number \| null`, `extractMatchKey()`는 型番 없으면 **상품명으로 폴백하지 않고 null** | `rakutenProduct.test.ts` — 50 checks |
| `src/scripts/verify-rakuten-product.ts` | 라이브 1회 확인 스크립트. 최대 6콜·1.1s 간격·읽기 전용. `productNo` 커버리지와 `salesItemCount` 생존 여부를 판정 | (라이브 전용) |
| `src/scripts/measure-coupang-rate-limit.ts` | 쿠팡 호출 한도 실측. 6→50/min 램프업, **최초 403/429에서 즉시 중단**, 일일 예산→카탈로그 상한 환산 | `measure-coupang-rate-limit.test.ts` — 39 checks |
| `src/scripts/seed-catalog-from-rakuten.ts` | 장르 순회 → `CandidateSeed` 생성. 이중 중복제거, 거절사유 집계 | `seed-catalog-from-rakuten.test.ts` — 37 checks |

실행 순서 (①이 ②③의 전제):

```
① npm run verify:rakuten-product                      # 라이브 1회, 읽기 전용
② npm run measure:coupang-limit -- --live             # 최초 거절에서 중단
③ npm run seed:from-rakuten -- --genre <id> --product-type camera --pages 3 --live
```

설계 원칙 (코드에 강제해둔 것):
- **"모름"이 숫자로 위장하지 못하게 한다.** `salesItemCount`가 null이면 판매처 수를
  0이나 1로 대체하지 않고 unknown으로 유지한다 → "N곳 중 최저가" 문구를 근거 없이
  쓸 수 없다. 필드명도 `purchasableListingCount`로 두어 "판매처 수"와 구분했다.
- **시드는 승인이 아니다.** 생성기 출력은 검색 입력일 뿐이고, 기존의 사람 승인
  단계(`docs/phase1-design.md` §4)를 우회하는 경로를 만들지 않았다.
- **型番 없으면 시드하지 않는다.** 상품명 기반 자동 동일성 판정은 설계상 금지 항목이다.
- **파라미터 오류와 호출 한도를 혼동하지 않는다.** 쿠팡은 거절된 파라미터를
  HTTP 200 + `rCode≠0`으로 돌려주므로, 이를 rate limit으로 집계하면 측정값이 거짓이 된다
  (D18L 회귀와 같은 종류의 실수) → `classifyAttempt()`에서 분리하고 테스트로 고정했다.

### 알려진 조건 (이 세션에서 고치지 않음)

`src/scripts/` 의 4개 테스트가 로컬에서 실패한다 —
`analyze-identifier-coverage` / `build-matching-baseline` / `evaluate-negative-filter` /
`measure-model-token-suggestion`. 원인은 코드 결함이 아니라 **데이터 부재**로,
`src/scripts/candidate-data/*-candidates.review.json` 이 저장소에 없다(GCS에 있고
`gcsCandidateIo.ts`로 읽는 구조). `.gitignore`에도 없으니 애초에 커밋되지 않은 파일들이다.
CI는 `tsc --noEmit`과 빌드만 돌리므로 **CI는 영향받지 않는다.**
이 때문에 §7의 "자동승인 레인 임계치 산출"(개발작업 #4)은 **BLOCKED** 상태다 —
429건의 원본 listing 텍스트 없이는 precision을 재측정할 수 없다. 해소 방법은 둘 중 하나:
(a) review.json 파일을 로컬에 두고 실행, (b) GCS 접근 자격으로 실행.
테스트를 "데이터 없으면 skip"으로 바꾸는 방식은 **의도적으로 택하지 않았다** — 실제
데이터 회귀를 조용히 감출 수 있어서, 사용자 판단 없이 바꿀 성질이 아니다.
