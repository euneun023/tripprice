# 라쿠텐 약관 위험 평가 + 안전성 수정 (2026-11-04)

범위: ① 라쿠텐 웹서비스 약관 대비 Tripprice 사업 모델의 위험 평가, ② 기존 코드의 데이터 안전성 결함 수정,
③ 라쿠텐 없이도 유지되는 부분의 점검. 시장조사·신규 아키텍처는 하지 않았다.
외부 API 호출, 외부 문의 발송, 운영 DB 변경, 데이터 삭제는 하지 않았다.

---

## 1. 약관 원문 확인 상태 — **차단됨, 조항 원문 0건 열람**

| 시도 | 결과 |
|---|---|
| WebFetch `webservice.rakuten.co.jp/guide/rule` (이전 턴) | DNS 해석 실패 (세션 허용 도메인 밖) |
| `curl https://webservice.rakuten.co.jp/guide/rule` (이번 턴, 1회) | 프록시 `CONNECT tunnel failed, response 403`, 0 byte |
| 검색 엔진 발췌 (이전 턴) | 약관 조항 문구를 돌려주지 못함 (무관한 타사 약관만 반환) |

**같은 방법을 반복하지 않았다.** 따라서 제3조 · 제8조 4항 · 제10조 1항 각 호의 **일본어 원문은 읽지 못했고**,
이 문서의 "조항 내용"은 (a) 이번 작업 지시문이 적어 준 조항별 요약과 (b) 이전 세션의 검색 발췌(11-03, B등급)뿐이다.
**영문 번역은 사용하지 않았고, 원문이 우선한다.** 이 평가는 "요약이 정확하다면"이라는 조건부이며,
어떤 조항도 Tripprice 전체의 적법/위법을 판정하는 근거로 쓰지 않는다.

분류 기준 (요청 사양):
- **A** 명시적으로 제한되는 행위 · **B** 허용 조건이 명시된 행위 · **C** 라쿠텐 서면 확인이 필요한 행위 · **D** 원문 미확인
- 원문을 읽지 못했으므로 **A로 확정할 수 있는 조항은 0건**이다. 지시문 요약이 정확할 경우 A에 해당할 수 있는 것은 `A*`로 표시한다.

## 2. Tripprice 사업 모델 (코드로 확인된 사실만)

| 사업 요소 | 현재 코드 상태 (사실) |
|---|---|
| 한국·일본 가격비교 | 구현됨 (`marketQuoteService`, 상품 페이지) |
| 쿠팡·라쿠텐 외 판매처 비교 | 설계 목표. 공급처 확장은 미착수 |
| 여러 쇼핑몰 구매 링크 | 리스팅별 `sourceUrl` 노출 구조 |
| 가격 **저장** + 주기 갱신 | **구현됨**: `source_listings.last_known_price`, `price_history`(append-only), 갱신 스케줄러 |
| 광고·제휴 수익화 | **코드에 없음** (AdSense·제휴 링크 구현 검색 결과 0건). 계획 단계 |
| 한국 거주 개인 운영 | 운영자 속성 |

→ **저장(제10조 1항 9호 관련)은 이미 운영 중인 동작**이다. 승인된 라쿠텐 리스팅 2건의 가격이 DB에 저장·이력화되어 있다.
이 문서는 그 데이터를 **삭제하지 않는다**. 다만 서면 확인 전에는 라쿠텐 출처 저장·표시를 **확대하지 않는 것**을 권고한다.

## 3. 조항별 위험 평가

충돌 가능성은 "지시문 요약이 정확하다면 Tripprice의 어떤 동작과 맞닿는가"에 대한 평가다.

| 조항 (지시문 요약, 원문 미열람) | 맞닿는 Tripprice 동작 | 충돌 가능성 | 분류 | 비고 |
|---|---|---|---|---|
| **제3조** 제휴 링크 의무 | 라쿠텐 상품으로 수익이 나는 표시 | 중 | **B** (조건 명시: 이전 세션 발췌 "수익 목적이면 제휴 링크 + 규약") · 상세 D | 보수는 일본 국내 계좌만 수령(발췌, B). 링크 사용 의무와 정산 가능은 **별개** |
| **제8조 4항** API 사용 부분에서 라쿠텐 외 사이트 링크 제공 제한 | 같은 화면에서 쿠팡 등 **타 몰 구매 링크** 병기 (가격비교의 핵심) | **높음** | **C** (`A*` 가능) | "API를 사용하는 애플리케이션 부분"의 범위 해석이 결정적. 해석으로 단정하지 않음 |
| **제10조 1항 4호** 라쿠텐 제휴 외 수익화 제한 | 광고·타 제휴 병행 계획 | **높음** | **C** (`A*` 가능) | 현재 코드엔 수익화 구현이 없어 *아직 위반 행위는 없음* |
| **제10조 1항 5호** 타 제휴 프로그램 이용 제한 | 쿠팡 파트너스 링크 병행 | **높음** | **C** (`A*` 가능) | 쿠팡 파트너스가 한국 정산의 유일한 현재 경로(11-03)라서 사업 모델과 직접 충돌 |
| **제10조 1항 6호** 경쟁 서비스 제공 제한 | 다중 몰 가격비교 서비스 | 중~높음 | **C** | "경쟁 서비스" 정의 원문 필요 (가격비교=경쟁인지 불명) |
| **제10조 1항 7호** API 정보의 이용·복제·변경 제한 | 정규화·환율 환산·병합 표시, 모델번호 추출 | 중 | **D → C** | 변환·가공이 "변경"에 해당하는지 원문 필요 |
| **제10조 1항 9호** 정보 저장·공유 제한 | 가격·재고·이력 DB 저장, 공개 표시 | **높음** | **C** (`A*` 가능) | **이미 운영 중인 동작**과 맞닿음. 가장 먼저 확인할 조항 |
| **제10조 1항 10호** 접근 제한 환경 이용 제한 | 공개 웹사이트(비로그인) | 낮음~중 | **D** | 로그인 뒤/제한 환경이 아니면 해당 가능성 낮으나 원문 미확인 |

**충돌 가능성이 높은 순서**: ① 9호(저장) ② 8조4항 + 10조1항 5호·4호(타 몰 링크·타 제휴·타 수익) ③ 6호(경쟁) ④ 7호(가공).
②는 "타 몰과의 비교"라는 서비스의 정체성과 같은 축이라, 원문 확인 결과에 따라 **라쿠텐 데이터를 이 서비스에 쓸 수 있는지 자체**가 갈린다.

**확인된 제한**: 없음 (원문 0건 열람).
**미확인**: 위 8개 조항 전부의 원문, 제6조·제7조의 부칙, 각 호의 예외 규정, 한국 거주 개인의 이용 자격 조항.

## 5. 데이터 상태 5단계와 코드의 대응

다섯 상태를 혼동하지 않도록 코드가 어디서 무엇을 보장하는지 정리한다.

| # | 상태 | 코드에서의 표현 | 이번에 확인한 보장 |
|---|---|---|---|
| 1 | 상품 후보로 발견됨 | `HOLD`/`REVIEW`의 `modelCode`/`variantId`, A의 시드 | 롤업(`product_aggregate`)은 여기까지만. 가격·URL을 갖지 않음 |
| 2 | 사람 검수 대상 | `REVIEW` + `ReviewBatch` | 권한 `granted` + 판매처 단위 가격 + 지역 명시일 때만 |
| 3 | 가격 비교 후보 | `comparableGroups` (`evaluateOfferEligibility`) | 재고 미상도 통과(공용 정책 F0). **구매 가능 확인 아님** |
| 4 | 현재 구매 가능 확인 | `availability: in_stock` 명시 → `comparableGroupsStockConfirmed`, `stockConfirmedRegions` | **이번에 분리.** 승인 앵커·미상은 세지 않음 |
| 5 | 공개 표시 허용 | — | **코드·스키마에 개념이 없음** (아래 §6 결함 F) |

### 확인된 5개 질문 (A~E)과 결과

| | 질문 | 결과 |
|---|---|---|
| **A** | 승인 상품의 `priceBasis`가 UNKNOWN인데 `AUTO_REFRESH`? | **결함 → 수정.** `approved_refresh_price_basis_unverified`로 HOLD (승인 기록 보존, 값은 갱신 안 함) |
| **B** | 재고 UNKNOWN이 "구매 가능"으로 표시/집계? | **부분 결함 → 수정.** ① 집계: `comparableGroupsStockConfirmed` 분리 ② **저장 경로**: 쿠팡 갱신이 `availability: true`를 하드코딩해 `last_known_availability=true`로 저장하던 것을 UNKNOWN(null)으로 변경 |
| **C** | 제품 집계가격이 판매처 가격처럼 비교/공개? | **추가 경로 없음.** 롤업·이전 버전 스냅샷 행·승인 키 일치 모두 HOLD로 확인, 회귀 테스트 추가 |
| **D** | 권한 UNKNOWN 공급처 상품이 공개 가능 상태로? | **결함 → 수정.** `ctx.providerRights`가 스냅샷에 구워져, 정책 항목을 지워도 이월 행이 `granted`로 남아 `AUTO_REFRESH`되던 문제. 이제 정책은 판정 시점에만 적용 |
| **E** | 미확인 신규 응답이 정상 값을 덮어씀? | **결함 → 수정.** ① 승인 리스팅: 통화 UNKNOWN은 HOLD ② 갱신 경로: 재고 UNKNOWN은 기존 `lastKnownAvailability`(true/false)를 덮어쓰지 않고, 기존 `OUT_OF_STOCK` 플래그를 해제하지 않음 ③ 라쿠텐 `availability`가 0/1이 아니면 `false`(품절)로 붕괴하던 것을 UNKNOWN으로 |

기존 승인 기록·가격·이력은 **삭제/대량 HOLD 하지 않았다.** 이미 저장된 쿠팡 `true`도 그대로 두며(보존), 앞으로 미확인이 새로 `true`로 승격되는 경로만 막았다.

### 수정되지 않은 한계 (정직한 기록)

- **F. 상태 5(공개 표시 허용)는 어디에도 강제되지 않는다.** `source_listings`/`sources`에 이용 권한 컬럼이 없고 표시 계층은 권한을 모른다.
  이미 승인된 라쿠텐·쿠팡 리스팅은 권한 확인 여부와 무관하게 표시된다. 해결은 DB 스키마 변경이 필요해 **이번 작업(운영 DB 변경 금지)에서 하지 않았다.**
- **G. 쿠팡은 구조적으로 상태 4에 도달할 수 없다.** 재고 필드가 없으므로 한국 쪽은 항상 "가격 후보"까지다.
  결과: 합성 실험의 `comparableGroupsStockConfirmed`는 0 (이전 보고의 "비교 가능 3,410그룹"은 *가격 후보* 수였다).
- **H.** 쿠팡 리스팅을 사람이 품절(`false`)로 표시하면, 이제 자동 복구되지 않는다(쿠팡은 `true`를 말할 수 없으므로). 수동 해제 필요 — 보수적 선택.
- **I.** `evaluate-candidates.ts`는 후보 평가용으로 `availability === 1`을 그대로 쓴다(미상이 "품절"로 표시되는 보수 방향, 저장 경로 아님). 변경하지 않음.
- 공용 `evaluateOfferEligibility`가 재고 미상을 통과시키는 정책(F0)은 의도된 설계라 변경하지 않았다.

## 6. 공급처 의존성 — 라쿠텐 없이 유지되는 부분

| 계층 | 라쿠텐 의존 | 근거 |
|---|---|---|
| 정규화·중복 제거·모델 식별·그룹화·검수 분류 (`listingIntakeService`) | **없음** | 파일에 "rakuten" 문자열 0건. 테스트 101건 중 매퍼 자체를 검증하는 구간을 제외하면 provider 무관 `mapGenericRow`로 구동 |
| 공통 형식 `ProviderListing` | 매퍼 2개(`mapRakutenItem`, `mapCoupangProduct`)만 | 새 공급처는 `mapGenericRow` + `priceBasis`/`usageRights` 선언으로 사용 가능 (**어댑터는 만들지 않음**) |
| 모델번호 **공급** | **높음** | 자동 공급원은 Rakuten Product Search `productNo`뿐. 없으면 피드의 `model`, 11번가/쿠팡 제목 토큰, Yahoo는 JAN |
| 갱신(`refreshService`) | 라쿠텐·쿠팡만 연결 | 다른 `sourceId`는 `No refresh adapter wired`로 예외. **새 공급처의 승인 리스팅은 어댑터 없이는 갱신 불가** |
| 상품 페이지 | `sourceId === "rakuten"` 분기 3곳(배송 안내) | 라쿠텐 제거 시 해당 분기만 영향 |

대체 가능 범위 (기존 코드·조사만 근거, 새 어댑터 없음):

| 공급처 | 재사용 가능한 것 | 막힌 것 |
|---|---|---|
| **Yahoo Shopping** | 인테이크 전 구간 (판매처 단위, JAN → 모델 식별 보조) | 어댑터 없음, JP ID·상업이용 문의 미해결, 응답 필드 미확인 |
| **11번가** | 인테이크 전 구간 (제목 토큰 매칭), 한국 복수 판매처의 유일한 후보 | 어댑터 없음, 약관 U |
| **판매자 공식 피드** | `mapGenericRow`가 그대로 수용 (`priceBasis:"seller_listing"` 선언 필수, 권한은 피드 제공자 허락 후 `granted`) | 몰별 영업. 다이빙 전문몰은 이쪽이 유일 경로 |
| 기타 | 같은 방식 | 권한 확인 후에만 |

`usageRights='granted'`는 **어떤 비테스트 코드에서도 부여하지 않는다** (감사 결과: 모든 `granted`는 오프라인 합성·저장소 정체성 실험 픽스처).
기존 데이터는 삭제하지 않았다.

**라쿠텐을 쓸 수 없게 되는 경우의 실제 손실**: 일본 판매처별 가격(코드로 증명된 유일 경로)과 모델번호 자동 공급. 이 둘은 Yahoo(승인 후)와 피드로만 대체되며, 현재는 둘 다 미확보다.

## 7. 판정

| 항목 | 판정 | 근거 |
|---|---|---|
| 라쿠텐 API **기술적** 사용 가능성 | **가능** | 판매처 단위 가격·URL·재고가 코드로 가동(A). 제품 검색 API는 라이브 미검증 |
| 라쿠텐 데이터 **상업적** 이용 가능성 | **HOLD** | 조항 원문 0건 열람. 8조4항·10조1항 4/5/9호가 사업 모델의 핵심과 맞닿음 → 서면 확인(C) 필요 |
| 다른 공급처로 확장할 가능성 | **조건부** | 매칭·검수 계층은 재사용 가능. 단 대체 공급처는 어댑터·승인·권한이 모두 미확보 |
| 실제 서비스 **공개** 가능성 | **HOLD** | 권한 확인 0곳 + 공개 표시를 막는 장치 부재(결함 F) + 쿠팡 재고 구조적 미상 |

코드 개발이 성공했다는 사실(안전성 결함 수정·테스트 통과)과 상품을 대량 확보할 수 있다는 사실은 별개다.
이 작업으로 늘어난 것은 **잘못된 승격을 막는 장치**이지 확보된 상품이 아니다.
